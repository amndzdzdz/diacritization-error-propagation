## Experiment: CATT token-level probability exposure

### Hypothesis

CATT's public inference interface exposes per-token (per-diacritic)
confidence scores or logits, sufficient to build the confidence threshold
that RQ4 (selective scoring by abstention) depends on.

### Methodology

Inspect the CATT public interface
([github.com/abjadai/catt](https://github.com/abjadai/catt)): run inference
on a sample sentence and check whether the returned output includes
token-level probabilities/logits, or whether they are reachable with a small
patch to the inference code. If not exposed and not easily patchable,
evaluate a substitute diacritizer from the Week 1–3 tool set (Shakkala,
Mishkal, Farasa) for the same property.

### Configuration

- Package: `catt-tashkeel==1.0.2` (PyPI), ONNX runtime backend, not the raw
  PyTorch training repo
- Checkpoint/variant: EO (`CATTEncoderOnly`), auto-downloaded on first use
  from `github.com/abjadai/catt/releases/download/v2/eo_model_onnx.zip`
  (72.1 MB)
- Sample input: the CATT README's own example sentence (news-domain MSA,
  ~110 characters)
- Environment: local sandbox, CPU (`onnxruntime-gpu` installed but no GPU
  used for this check), `torch` added only because it was anticipated to be
  needed — it turned out the shipped package is ONNX-only and torch was not
  actually required for this check
- Script: `scripts/check_catt_probabilities.py`

### Results

`catt_tashkeel.CATTEncoderOnly`/`CATTEncoderDecoder` do **not** publicly
expose confidence: `do_tashkeel()`/`do_tashkeel_batch()` return decoded text
only. However, reading the installed package source
(`catt_tashkeel/models.py`) shows `BaseONNXTashkeel._process_batch` computes
`preds = self._run_decoder(...)` — raw per-class logits over the 18-way
diacritic vocabulary at every character position — and only *then* applies
`np.argmax(preds, axis=-1)` and discards `preds`.

Calling the same (non-public, underscore-prefixed) methods directly —
`_preprocess_text`, `_prepare_batch_input`, `_run_encoder`, `_run_decoder` —
and applying softmax ourselves instead of argmax recovers a full
per-character confidence distribution. The reconstructed diacritized text
from this path was byte-for-byte identical to `do_tashkeel()`'s output on
the test sentence, confirming the right tensor was captured. Per-character
confidence on the sample sentence ranged from 0.4765 to 1.0000 (mean
0.9631) — i.e. genuinely informative, not uniformly saturated at 1.0, which
is what RQ4's threshold sweep needs.

### Observations

- The public API surface (`do_tashkeel`) is insufficient; the private
  ONNX-session methods are sufficient and are stable enough today to build
  on, but they are not a supported interface — a `catt-tashkeel` version
  bump could rename or restructure them without notice.
- The EO model's decoder is non-autoregressive (single encoder + decoder
  pass over the whole sequence), which is why extracting logits for it was
  a single extra ONNX call. The ED model's decoder is autoregressive
  (`_run_decoder` called once per output position in a loop); the same
  technique will work but the confidence for position *i* would need to be
  read off at the step where token *i* was generated. Not yet checked
  empirically for ED — EO was sufficient to answer the week-1 question.
- Confidence was lowest on genuinely ambiguous cases in the sample (e.g. a
  borrowed/transliterated word fragment scored 0.4765; a case-ending-like
  position on a common word scored 0.5018), which is at least directionally
  consistent with the plan's concern that case endings may attract
  confidently-wrong rather than uncertain predictions — worth re-checking
  at scale once RQ4 is actually run, not concluded from one sentence.

### Conclusion

**CATT exposes usable token-level confidence, via undocumented but working
internals — no substitute diacritizer is needed for RQ4.** Decision:
proceed with CATT for the abstention experiment. Before Week 4–6 (when the
real diacritizer pipeline is built), vendor this extraction logic into
`src/arabic_mdd/diacritizers/` behind a small wrapper with its own tests,
rather than depending on catt-tashkeel's private methods at pipeline-build
time — this check only needed to establish feasibility, not build the
production interface. Also confirm the same technique on the ED checkpoint
before committing to which variant RQ4 uses, since CATT's own numbers
(novelty-check.md) show ED is the more accurate variant.

## Experiment: mHuBERT + BiLSTM + CTC baseline reproduction (week-3 gate)

### Hypothesis

Running the organizers' own S3PRL-based training recipe
(`scripts/baseline_reproduction/`, vendored per the week 2 decision) with
its vendored, unmodified `config/sws.yaml` reproduces the published
organizer baseline at F1 ≈ 0.4414 ± 0.02 on `QuranMB.v2`.

### Methodology

1. `run/train_baseline.slurm` (`sbatch`, user's cluster, 1 GPU): environment
   setup (`run/prepare_baseline.sh` — Python 3.8 venv, S3PRL install,
   `Iqra_train` + `Iqra_TTS` download/merge into the 131h train split,
   bucketing/TSV prep, config wiring), then
   `run_downstream.py -m train -c downstream/ctc/cv_config/sws.yaml -p hubert_base_per -u hubert_base -d ctc`
   for the full `total_steps: 200000` in the vendored config, then
   `run_downstream.py -m evaluate -e hubert_base_per/dev-best.ckpt`.
2. `run/quranmb_gate_check.slurm`: two-stage gate check against the
   trained `dev-best.ckpt`.
   - Stage A (S3PRL venv, GPU):
     `scripts/baseline_reproduction/quranmb_gate_inference.py` runs the
     checkpoint over every `safikhan/quran_mbv2_formatted` utterance
     (materialized to temp wavs one at a time) and writes
     `run/quranmb_predictions.json` (`{id: predicted_phoneme_string}`).
   - Stage B (this project's own uv/Python-3.12 env):
     `scripts/quranmb_gate_score.py` loads that JSON, joins against
     `arabic_mdd.data.quranmb.load_ground_truth()`, scores with
     `score_predictions` + `compute_metrics`
     (`src/arabic_mdd/metrics/hierarchical.py`), and prints the gate
     verdict.

### Configuration

- Upstream: `-u hubert_base` (S3PRL's own flag name in the organizers'
  training command — not independently verified against S3PRL's upstream
  registry to confirm it resolves to a genuine multilingual mHuBERT
  checkpoint rather than an English-only HuBERT; **flagged as open,
  unresolved before this entry was written**, see Observations)
- Config: `scripts/baseline_reproduction/config/sws.yaml`, vendored
  verbatim (Adam, lr 1e-4, no scheduler, batch size 16, specaug on,
  BiLSTM projection head dim [1024, 1024], `total_steps: 200000`,
  `eval_step: 5000`)
- Training data: `IqraEval/Iqra_train` (79h) + `IqraEval/Iqra_TTS` (52h),
  merged per `run/prepare_baseline.sh` step 4 — not independently verified
  against the organizers' actual training mix (**also flagged as open**)
- Checkpoint scored: `hubert_base_per/dev-best.ckpt`, from a training run
  that reached 200000/200000 steps (confirmed complete by the user, 22 Sep
  2026)
- Eval set: `safikhan/quran_mbv2_formatted` (1,643 utterances) — all 1,643
  predictions matched a ground-truth id (full coverage, no join loss)

### Results

```
counts: MDDCounts(ta=42324, fr=7489, fa=763, tr=2818, correct_diagnosis=1661, error_diagnosis=1157)
precision: 0.2734  recall: 0.7869
FAR: 0.2131  FRR: 0.1503  DER: 0.4106
detection accuracy: 0.8455
F1: 0.4058  (gate: 0.4414 +/- 0.02 -> [0.4214, 0.4614])
GATE: FAIL
```

F1 = 0.4058 is ~0.0356 below the lower bound of the tolerance band
(0.4214) — outside ±0.02, a narrow but real miss, not a rounding artifact.

### Observations

- Recall (0.7869) well exceeds precision (0.2734), and FAR (0.2131) is
  noticeably higher than FRR (0.1503) — the model over-flags correct
  pronunciations as errors more than it misses real ones. Not a
  degenerate/broken model (detection accuracy 0.8455 is reasonable), but
  systematically miscalibrated relative to the published number.
- Two unverified assumptions could each explain some or all of the
  shortfall and were not checked before this run:
  1. Whether S3PRL's `-u hubert_base` upstream string actually resolves to
     a multilingual mHuBERT checkpoint (as the paper's prose implies) or
     to a different/generic HuBERT variant — not confirmed against
     S3PRL's upstream registry.
  2. Whether the `Iqra_train` + `Iqra_TTS` merge in
     `run/prepare_baseline.sh` matches the organizers' actual training
     mix (right proportions, no duplication/gap introduced by the merge
     step) — not independently audited.
- Full training run (200000/200000 steps) completed before this checkpoint
  was scored, so this is not a "check back later, still training" result —
  it reflects the fully-trained model.

### Conclusion

**Gate fails as currently measured: F1 = 0.4058 vs. required
[0.4214, 0.4614].** Per the week-3 gate criterion in
`docs/mdd-paper-project-plan-v2.md` ("if a fully specified published
baseline cannot be reproduced, nothing downstream is trustworthy"), this
needs debugging before treating any downstream result as trustworthy.
Next steps, in order: (1) verify the `-u hubert_base` upstream identity
against S3PRL's registry; (2) audit the `Iqra_train`/`Iqra_TTS` merge
against the organizers' actual training mix; re-run the gate check only
after ruling both out, rather than concluding a genuine reproduction
failure prematurely.
